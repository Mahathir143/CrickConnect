Architectural & System Strategy

CrickConnect: System Approach & Technical Foundations

A rigorous examination of design principles, low-latency synchronization models, Chromium Embedded Framework (CEF) memory guardrails, and cryptographic broadcast safety.

1. The Problem Space & Broadcast Realities

Streaming live cricket differs substantially from standard web dashboards. A live broadcast production environment presents hard engineering constraints:

Sub-150ms Latency Requirement

When the commentator on stream calls a "SIX!", the broadcast overlay graphic must pop on screen synchronously. Latencies above 300ms result in jarring, desynchronized visual artifacts that degrade viewer immersion.

OBS / CEF Memory Leak Hazards

OBS Studio and Prism Live Studio render browser sources via the Chromium Embedded Framework (CEF). Typical React SPAs with active intervals, complex DOM lifecycles, and re-renders leak memory, crashing the OBS scene during 4-to-8-hour continuous matches.

Cricket Rule Matrix Complexity

Unlike sports with monotonic score increments, cricket has non-linear dependencies: Wides, No-Balls with Free-Hits, composite extras, 11 dismissal modes, and the modern 2022 ICC strike rule on catches.

Network Volatility at Stadiums

Grassroots and semi-pro grounds often experience intermittent cellular connectivity. The scoring client must maintain offline queueing, and the broadcast overlay must gracefully degrade without flashing white error screens.

2. Core Architectural Philosophy: Event Sourcing vs. Mutable State

Traditional scoring systems store a single mutable snapshot (e.g., total_runs += runs). In real-time broadcasting, this leads to catastrophic state drift whenever an umpire reverses a decision or a scorer makes an accidental input error.

CrickConnect Architectural Decision: All match progression is modeled as an append-only immutable event stream (Event Sourcing). The live match state displayed on overlays is a deterministic pure projection derived from the ball log.

┌─────────────────────────┐       ┌──────────────────────────────┐       ┌─────────────────────────────┐
│   Scorer Action (Ball)  │ ───>  │  Append to match_balls log   │ ───>  │ Project into Live Snapshot  │
└─────────────────────────┘       └──────────────────────────────┘       └─────────────────────────────┘
                                                 │                                      │
                                        (Immutable Record)                    (Broadcast via WS/Chan)
                                                 │                                      │
                                                 ▼                                      ▼
                                  ┌──────────────────────────────┐       ┌─────────────────────────────┐
                                  │   Undo = Pop Last Ball Event │ ───>  │  Recompute Projection (0ms) │
                                  └──────────────────────────────┘       └─────────────────────────────┘

Advantages of Event Sourcing in CrickConnect:

  • Infallible Multi-Level Undo: Undoing ball 4 of an over does not just subtract runs; it cleanly restores the previous striker, bowler figures, and maiden over eligibility.
  • Ball-by-Ball Audit Trail: Comprehensive timeline used for automated wagon wheels, worm charts, and post-match scorebooks.
  • Deterministic Replay: Any match can be replayed from ball 1 to test new overlay designs or regenerate graphics without altering raw data.

3. OBS Browser Source Strategy: Zero-Memory-Leak Engineering

To ensure 100% broadcast stability during 8-hour continuous tournament broadcasts, the Overlay Client applies strict browser source guardrails:

Design Concern Conventional Web App Flaw CrickConnect CEF Solution
Alpha Channel Transparency White flash during DOM hydration or state switches. Strict CSS root alpha html, body { background: transparent !important; } and pre-rendered inline SVGs.
GPU Compositing CPU-bound repaints on top, left, width mutations. Exclusively CSS3 hardware transforms: transform: translate3d(), will-change: transform, opacity.
Animation Cleanup Lingering Framer Motion listeners and hidden DOM nodes. Stinger elements unmount completely from DOM after their 3.5s animation duration finishes.
RAM Usage Over Time 500MB - 1.2GB RAM leak over 4 hours. Stable flat profile: < 90MB RAM footprint over 8+ hours continuous operation.

4. Real-Time Synchronization Strategy

CrickConnect provides dual synchronization channels tailored for both local single-machine setups and multi-location cloud broadcasts:

Level 1: Zero-Config Local BroadcastChannel

When the Scorer Desk and OBS Browser Source run on the same workstation or local network, state is propagated via the native BroadcastChannel('crickconnect_live') API. Latency is < 5ms with zero cloud roundtrip or bandwidth cost.

Level 2: Cloud Pub/Sub (Supabase Realtime / WebSockets)

For remote scorers and multi-cam broadcast trucks, events publish to isolated channel partitions: match:{matchId}:live. WebSockets push updates in < 120ms with automatic heartbeat and reconnection backoff.

Connection Drop Handling: If the venue internet cuts out, the overlay freezes on its last valid frame. It never presents a 404 or connection error on the broadcast feed, and seamlessly re-syncs once connection returns.

5. Security & Multi-Tenant Governance

Live streams are public, meaning match IDs can be scraped. To prevent malicious tampering:

  • Cryptographic Capability Tokens: Overlay URLs require a read-only token: /overlay/:id?token=sec_ro_.... The overlay endpoint lacks write scopes, preventing any scoring alteration.
  • Role-Based Access Control (RBAC):
    • Super Admin: Tournament configuration and team review.
    • Scorer: Restricted strictly to entering balls for their assigned match.
    • Broadcaster / Graphics Producer: Can toggle overlay graphics (milestones, DRS, sponsor bugs) but cannot modify scores.
  • Upload Sanitization: Public team registrations enforce strict MIME filtering (PNG, JPEG, WebP only), rejecting SVGs to eliminate stored XSS vectors. Image payloads are resized server-side.
